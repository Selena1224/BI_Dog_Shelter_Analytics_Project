01 · Business problem

Critical shelter data existed, but not in one decision-ready view.

Adoption, foster, veterinary, volunteer, and shelter information was distributed across operational tables. Staff could record transactions, but answering cross-functional questions required manual work and offered limited visibility into adoption outcomes, medical spending, volunteer support, and time in care.

The analytical objective

Create a reliable BI environment where shelter leaders can explore multiple operational areas together, identify patterns quickly, and allocate limited space, outreach, volunteer support, and veterinary resources more effectively.

03 · Measures and calculations

The cube became a decision-support tool through custom metrics.

Raw counts were not enough. The project added calculated measures that translated operational events into metrics shelter leaders could understand and act on.

Placement performance

Adoption Rate

Compared adoption records with the total number of dogs to evaluate placement effectiveness over time.

[Adoption Fact Count] / [Dogs Count]
Animal profile

Average Dog Age at Adoption

Corrected default sum behavior by dividing total dog age by the adoption count.

SUM([Dog Age]) / [Adoption Fact Count]
Foster operations

Average Foster Duration

Calculated each placement's elapsed days and then summarized typical time spent in foster care.

AVG([Foster End Date] - [Foster Start Date])
Medical resources

Veterinary Cost per Dog

Converted total treatment costs into an average expense per animal receiving care.

[Treatment Cost] / [Dogs Count]
Community support

Volunteer Contribution Ratio

Measured each shelter's share of total volunteer hours to identify support imbalances.

[Hours] / SUM([Hours])
Operational volume

Core Counts

Tracked adoption, foster, veterinary, and volunteer activity volumes across dimensions and time.

COUNT(Fact Records)
04 · Technical build walkthrough

What was built behind the dashboard.

This was not only a reporting exercise. The project redesigned the underlying data structure, resolved model conflicts, configured multidimensional relationships, and handled calculation behavior across SSAS and Excel.

01

Audit the Microsoft Access operational model

The source database contained transactional tables for dogs, adopters, shelters, foster homes, rescue organizations, veterinary visits, adoptions, and volunteer activity. Primary and foreign keys were reviewed, inconsistent date formats were corrected, validation settings were improved, and redundant fields were removed.

Technical focus: data integrity, relationship validation, field sizing, date consistency, and removal of attributes that could create ambiguity during cube development.
02

Create a reusable Date Dimension

Adoptions, foster placements, vet visits, and volunteer activity all required time analysis. A centralized calendar dimension was created so the same hierarchy could support multiple business events.

DateDimension
├── DateID
├── FullDate
├── YearNumber
├── QuarterLevel
├── MonthName
├── MonthNumber
├── DayNumber
└── WeekdayName
Challenge solved: using Full Date as both a key and hierarchy level initially caused duplicate-level conflicts. The hierarchy was simplified and later improved by separating a surrogate DateID from descriptive date attributes.
03

Move the cleaned source into SQL Server

The Access database was exported to SQL Server to create a stable relational foundation for Analysis Services. This separated the operational source from the analytical environment and prepared the data for dimensional modeling.

Why it mattered: SQL Server provided a more appropriate foundation for cube processing, scalable querying, and consistent deployment than analyzing directly from an operational Access file.
04

Design the data mart and measure groups

The analytical design centered four fact-like processes: Adoption Fact, Foster History, Veterinary Visits, and Volunteer Activity. Shared descriptive dimensions provided context for filtering and grouping.

Measure Groups
1. Adoption Fact
2. Foster History
3. Veterinary Visits
4. Volunteer Activity

Shared Dimensions
Dogs, Shelters, Adopters,
Foster Homes, Rescue Organizations,
Date Dimension
Design principle: fact records captured measurable events, while dimensions supplied the who, what, where, and when required for drill-down analysis.
05

Configure role-playing date dimensions

The same Date Dimension was reused in different semantic roles, including Adoption Date, Foster Start Date, Foster End Date, Visit Start Date, Visit End Date, and Volunteer Activity Date.

Result: users could analyze each process by the correct business date without creating separate physical calendar tables for every event type.
06

Build drill-down hierarchies

Hierarchies transformed long attribute lists into intuitive navigation paths. Users could start with a broad view and progressively investigate a specific time, animal type, or location.

Date:     Year → Quarter → Month → Day
Dog:      Breed → Size → Gender
Shelter:  State → City → Shelter Name
User benefit: shelter staff could explore data without writing SQL or MDX queries.
07

Define calculated measures in SSAS

Custom calculations handled adoption rate, foster duration, medical cost per dog, and volunteer contribution. Some averages required explicit sum-divided-by-count logic because the default aggregate behavior returned misleading totals.

Adoption Rate =
  [Measures].[Adoption Fact Count]
  /
  [Measures].[Dogs Count]

Veterinary Cost per Dog =
  [Measures].[Treatment Cost]
  /
  [Measures].[Dogs Count]
Analytical lesson: a measure can be mathematically correct at the row level but still behave incorrectly when aggregated across dimensions. Context-aware validation is essential.
08

Troubleshoot deployment and aggregation issues

The build encountered localhost configuration problems, hierarchy warnings, duplicate attributes, key conflicts, and incorrect averages. The model was refined by cleaning attribute relationships, disabling redundant fields, restructuring date levels, and supplementing a few calculations in Excel when cube behavior remained inconsistent.

What this demonstrates: practical BI development includes debugging infrastructure, metadata, aggregation logic, and user-facing outputs, not only creating charts.
09

Connect Excel to the deployed cube

Excel PivotTables and Pivot Charts served as the reporting interface. Users could drag measures and dimensions into views, apply slicers, and navigate hierarchies interactively.

06 · Dashboard insights

The reporting layer translated the cube into operational action.

Adoption and foster patterns by dog size

Large dogs were fostered more frequently, while small and medium dogs were adopted at nearly the same rate. This can influence housing capacity, foster recruitment, and targeted outreach.

Veterinary resource use by breed

German Shepherds showed the highest total treatment costs and longest stays, while Poodles and Beagles were adopted quickly but still required above-average medical care.

Volunteer support by shelter

Hours and contribution ratios revealed which facilities had strong community support and which locations might require additional volunteer recruitment.

Seasonal adoption trends

Date hierarchies enabled shelters to identify slow adoption periods and plan outreach campaigns when placement activity declined.

Average age at adoption

Breed and size breakdowns supported analysis of which dogs tended to wait longer and where promotional attention could be focused.

Medical cost per dog

Average treatment cost created a clearer resource-allocation metric than total expense alone, especially when comparing shelters or animal groups.

07 · Lessons learned

Technical obstacles became design lessons for future BI systems.

What went well

End-to-end integration

The project successfully connected a cleaned relational source, dimensional model, SSAS cube, measures, and Excel visualizations.

What was difficult

Keys, dates, and aggregation

Date hierarchy conflicts, duplicate attributes, deployment configuration, and non-additive averages required repeated debugging.

Next iteration

Design surrogate keys earlier

A dedicated DateID, stronger attribute relationships, more cube-native calculations, structured addresses, and broader animal coverage would improve scalability.

Project conclusion

Business intelligence can help shelters act faster on the information they already collect.

This project demonstrates data cleaning, relational modeling, data warehousing, multidimensional cube development, MDX-style calculated measures, hierarchy design, deployment troubleshooting, and self-service reporting. The result is a system that makes adoption, foster, veterinary, and volunteer patterns easier to see and easier to act on.
